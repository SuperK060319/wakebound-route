# 《潮痕航路》家书与微信分享对抗性验收

审核日期：2026-08-22  
审核范围：`family-letter.html`、`health-content.js`、`game.js` 中家书入口，以及手机横屏下的链接复制、长图生成、字体和分享路径。  
变更边界：本任务只记录问题与验收方法，没有修改核心游戏或家书实现。

## 结论

**当前状态：有条件不通过，修复 3 个发布阻塞项后再进微信实机验收。**

已经成立的部分：称呼与署名不会从查询参数回填；游戏生成的家书入口只带 `topic` 和 `festival`；本地浏览器可以生成 1080×1600 PNG；页面没有横向溢出；健康事实、来源和免责声明来自统一数据源。

发布前必须先修：

1. 称呼会被作为 HTML 解析，存在输入注入风险。
2. “通用链接”会保留原地址的 `#片段`，与“只包含健康主题和节日”的隐私承诺冲突。
3. 复制与长按保存只在普通 Chromium 环境部分验证，尚无微信 iOS、微信 Android 的真实成功证据；不能仅凭成功提示上线。

## 审查环境与证据边界

- 通过本地 HTTP 服务打开页面，避免 `file://` 与正式发布行为混淆。
- 模拟横屏视口：844×390（DPR 1.5）与 667×375。
- 844×390 下页面 `scrollWidth = clientWidth = 829`，无横向溢出；但总高 1135px，操作面板从约 y=239px 才开始，两个分享按钮均不在首屏完整可见区域。
- 667×375 下触发单列布局，操作面板排在信纸前；页面总高约 1427px，保存图片按钮仍在首屏下沿之外。
- 最长称呼/署名压测中成功生成 1080×1600 PNG，浏览器内显示的 Data URL 长约 343,766 字符。
- 本次没有可控制的真实微信 iOS/Android WebView，因此“微信长按保存”“微信内复制”“链接卡片预览”均列为待实机项，而不是判定通过。
- 国家卫生健康委主来源可以从官方搜索结果追溯；自动直接请求曾返回 412，因此还需用微信内置浏览器实际点击来源链接，不能据此断言链接已失效。
- 健康内容准确性与奖励隐喻已由同目录《健康知识审核报告》单独审查；本文不重复扩大医疗结论。

## 问题清单

### F-01｜P0 发布阻塞：称呼被拼入 `innerHTML`

**位置**：`family-letter.html` 第 43 行附近，`render()`。

**复现步骤**：

1. 打开家书页。
2. 在“写给谁”输入 `<b>家人</b>`。
3. 检查家书正文。
4. 实测正文中出现了一个真正的 `<b>` 节点，而不是原样显示尖括号。

`maxlength="20"` 不是安全边界；短事件载荷仍可能落在 20 字符内。虽然称呼默认不来自 URL，这仍然会让从微信粘贴的异常文本改变 DOM，且破坏用户输入的忠实呈现。

**最小修改建议**：不要把含用户输入的完整家书交给 `innerHTML`。用 `textContent` 和 `document.createTextNode()` 组装称呼、前后文；只有健康事实单独创建 `<strong>` 元素。不要采用手写替换 `<`、`>` 的方式兜底。

**验收**：输入 `<b>家人</b>`、`A&B`、引号、emoji 和 20 个汉字后，页面只出现文本节点；`#letter-body` 内除产品主动创建的一个 `<strong>` 外没有新增标签或事件属性。

### F-02｜P0 发布阻塞：复制链接会遗留 URL Fragment

**位置**：`family-letter.html` 第 44 行附近，`publicUrl()`。

**复现步骤**：

1. 打开：`family-letter.html?topic=activity&festival=qixi&recipient=王妈&sender=小李&tracking=秘密#sender=隐私`。
2. 页面中的称呼和署名保持默认值，说明查询参数没有被回填，这一点通过。
3. 执行当前通用链接逻辑。
4. 得到：`family-letter.html?topic=activity&festival=qixi#sender=隐私`。

查询参数会被清空重建，但 `url.hash` 没有清空，所以“通用链接只包含健康主题和节日”的说明并不严格成立。Fragment 通常不会发送给服务器，但会被复制给收件人、进入聊天记录，并可被前端脚本读取；隐私目标不能把它视为无害。

**最小修改建议**：在重建查询参数前增加 `url.hash = ''`；继续只写入白名单参数 `topic`、`festival`。不要把称呼、署名、自由文本、时间戳或追踪参数加入分享 URL。

**验收**：对带任意查询参数和任意 `#片段` 的入口点击复制，结果必须恰好只有同源家书路径、一个合法 `topic`、一个合法 `festival`，且不含 `recipient`、`sender`、其他参数和 `#`。

### F-03｜P0 发布阻塞：微信复制成功与长按保存均未形成闭环证据

**位置**：`family-letter.html` 第 45、47 行附近。

**复现与现象**：

- 普通 Chromium 中点击“复制通用链接”后页面显示“已复制”，但自动化会话读取到的剪贴板为空；这可能是测试环境的剪贴板隔离，也说明不能用页面提示代替“粘贴回读”验收。
- 当前失败兜底是 `prompt()`。微信 WebView 对 Clipboard API、系统弹窗和长按选择的表现会因 iOS/Android 版本而异。
- 长图已经在普通浏览器生成并显示，但尚未证明微信中长按菜单会出现“保存图片”，也未证明保存后的相册图片完整。

**最小修改建议**：

1. 复制失败时不要只弹 `prompt()`；在页面内显示只读文本框，自动选中链接，并写清“长按链接 → 复制”。
2. 长图生成后进入简洁的全屏预览层，图片本身占主要区域，明确提示“长按图片保存到手机”；保留关闭和重新生成入口。
3. 仍以 `<img>` 为微信保存载体；不要只提供 `download` 属性，因为微信通常不会按桌面下载流程处理。
4. 成功提示必须由真实动作触发；发布验收时必须把复制结果粘贴回聊天输入框，并从系统相册重新打开保存图片。

**验收**：微信 iOS 与 Android 各完成一次“复制 → 粘贴 → 打开”和“生成 → 长按 → 保存 → 相册打开”，图片无裁切、黑屏、透明底或文字缺失。

### F-04｜P1：844×390 横屏下，分享操作不在首屏

**位置**：`family-letter.html` 第 10 行内联样式。

**复现步骤**：

1. 将视口设为 844×390 横屏。
2. 打开运动主题、七夕家书。
3. 页面仍使用两列；信纸宽约 393px、高约 1067px，操作面板 y≈239px、高约 657px。
4. 首屏只能看到信纸上部与操作面板标题附近，分享按钮需要明显向下滚动。

问题根因不是横向溢出，而是只有 `max-width:800px` 的单一断点；常见横屏手机宽度大于 800px，但高度很小。`align-items:center` 又把操作面板垂直居中到长信纸旁边。

**最小修改建议**：增加 `@media (orientation:landscape) and (max-height:560px)`：页面改为 `align-items:start`，缩小外边距与面板垂直间距；必要时把操作面板放到第一列/顶部，或让面板成为高度受控的独立滚动区。不要压缩按钮到小于 44px 高。

**验收**：844×390、740×360、667×375 三档均无横向滚动；称呼、署名和两个主要按钮能在清楚的滚动路径内到达，不被地址栏、键盘或信纸覆盖；首次进入时至少能看到“这是可编辑家书”及一个明确的分享动作。

### F-05｜P1：未使用安全区，横屏刘海/圆角可能压住内容

**位置**：已有 `viewport-fit=cover`，但 CSS 未使用 `env(safe-area-inset-*)`。

**复现方式**：在有刘海或灵动岛的 iPhone 横屏进入，分别让刘海位于左右两侧，观察标题、信纸边缘、表单和按钮。

**最小修改建议**：页面四边 padding 在现有值上叠加或取最大值：`max(14px, env(safe-area-inset-left))` 等；全屏长图预览也使用安全区。不要只给 `body` 增加固定左边距。

**验收**：iPhone 横屏左右旋转各一次，所有可点击控件、标题和隐私提示均未进入刘海、圆角和 Home 指示条区域。

### F-06｜P1：微信分享卡片缺少静态元数据

**位置**：`family-letter.html` 的 `<head>` 只有普通 `title` 与 `description`，没有 `og:title`、`og:description`、`og:image` 等静态分享信息。

微信抓取链接卡片时不应假设会运行页面 JavaScript；当前由 JS 改写的“春节家书/七夕家书”标题很可能不会进入聊天卡片。结果可能是泛化标题、无缩略图或平台自行抓图，降低收件人的打开意愿。

**最小修改建议**：先提供不含个人信息的统一静态卡片：固定标题、克制描述和公开可访问的绝对 HTTPS 缩略图。若以后要按节日动态卡片，应由服务端/预渲染页面按白名单参数输出，仍禁止加入称呼署名。

**验收**：把正式 HTTPS 链接分别发给微信 iOS/Android 的文件传输助手和真实会话；卡片标题、摘要、缩略图一致，不出现姓名，不把健康主题误写成个体诊断。

### F-07｜P1：长图高度和来源位置是固定值，内容扩写后会静默裁切

**位置**：`saveImage()` 固定 `canvas.height=1600`，来源从 y=1490 开始，署名被压到最大 y=1400。

当前四主题与现有字数下可以生成；但 `health-content.js` 明确标注为“安全可改区”，未来扩写 `fact`、`familyAction`、节日祝福或免责声明后，正文可能与署名/来源重叠，或超出画布。当前没有溢出检测，用户仍会看到“已生成”的成功提示。

**最小修改建议**：先测量并保存每段换行结果，再按“标题 + 正文 + 署名 + 来源 + 底部留白”计算画布高度；设置合理最大高度，超限时减小字号或明确报错，不要静默截断。来源位置必须跟随正文而不是固定 y=1490。

**验收**：4 个主题 × 6 个节日 × 默认/20 字称呼署名共 48 组全部生成；文字间不重叠，来源完整，底部留白不少于 60px。

### F-08｜P2：小字与字体回退不适合微信小屏

**位置**：标签和隐私说明 10px，来源 11px；正文使用 `Georgia, "Noto Serif SC", serif`，Canvas 只写 `serif`/`sans-serif`。

Georgia 不包含中文字形，Noto Serif SC 在多数设备并非必装，最终中文会依系统回退；网页和 Canvas 还可能落到不同字体。10–11px 在小屏横屏、微信字体缩放或中老年用户场景下可读性不足。

**最小修改建议**：中文字体排在明确的系统中文字体栈中；Canvas 与页面共用同一套字体声明，并在生成前等待 `document.fonts.ready`（若将来加入 Web Font）。标签、来源、隐私说明至少提升到 12–13px，正文移动端不低于 16px；同时测试微信“标准/较大”字体设置。

**验收**：iOS、Android 各截取网页与相册长图对比；中文无方框、缺字、异常粗细或明显换行漂移；系统大字体下不遮挡按钮和来源。

### F-09｜P2：权威来源在微信中的可达性未验证

**位置**：`health-content.js` 第 7 行来源链接，`family-letter.html` 第 21 行外链。

源地址与发布机构正确，现有健康事实也已有独立审核报告支持。但国家卫生健康委页面对不同请求头可能返回不同结果；本次自动直接请求曾遇到 412，不能把桌面可检索等同于微信 WebView 可打开。

**最小修改建议**：保留官方原始链接，不做不透明跳转；在来源旁展示机构、文档名和“2024年版”，即使外链暂时打不开也能识别出处。可增加“链接打不开时复制标题搜索”的轻提示，但不要镜像或改写成非官方来源冒充原文。

**验收**：微信 iOS/Android 各点击一次来源链接；能打开官方页面或得到明确的平台提示，返回家书时输入内容仍在；失败时用户仍能看到完整来源名称。

## 最小修改顺序

1. **先封安全与隐私**：去掉用户输入的 `innerHTML`；`publicUrl()` 清空 hash 并白名单化参数。
2. **再补微信兜底**：页面内可选中链接、全屏长图预览、失败提示。
3. **再做横屏 CSS**：低高度横屏断点、安全区、字号与按钮触控尺寸。
4. **最后补分享卡片与动态画布**：静态 OG 元数据、按内容计算长图高度。
5. **完成真实微信双端验收**，再把文案从“可以直接发到微信”升级为确定性承诺。

## 建议的放行标准
